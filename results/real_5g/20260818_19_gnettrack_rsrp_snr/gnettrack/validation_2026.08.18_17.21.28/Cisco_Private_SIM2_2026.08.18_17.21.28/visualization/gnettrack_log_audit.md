- Primary log: `Cisco_Private_SIM2_2026.08.18_17.21.28.txt`
- Verbose log: `Cisco_Private_SIM2_2026.08.18_17.21.28_verboselog.txt`
- GPS samples: 18 (2026.08.18_17.21.28 through 2026.08.18_17.21.44)
- Exported serving RSRP (dBm): -96 to -96; 1 unique value(s)
- Exported serving SNR (dB): not populated
- Recovered freshest-record RSRP (dBm): -96 to -96; median -96.0
- Recovered freshest-record SINR (dB): 23 to 24; median 24.0
- Registered verbose Android cell records: 32 NR, 0 LTE

## Findings

1. The exported serving RSRP and SNR are frozen for the entire drive. The verbose log contains changing NR CellInfo measurements, so the constant map layers generated by G-NetTrack are not credible coverage measurements.
2. The dashboard's default layer reconstructs the trace by selecting the registered CellInfo object with the newest Android radio timestamp, retaining it only when it is NR, then matching it to the nearest GPS sample (maximum accepted gap: 3 seconds).
3. G-NetTrack labels the Cisco session `NSA` internally, but Android reports data RAT `20 (NR_SA)`, PS registration directly on NR, and display override `NONE`. The LTE records are an AT&T registration during a roughly 80-second Cisco coverage interruption, not a simultaneous LTE anchor; the recovered NR map leaves this interval blank.
4. Enabling G-NetTrack's Dual SIM support and `5G dual mode fix`, selecting Data SIM 2 (the active Cisco eSIM's Android slot), disabling `5G NSA mode fix`, and enabling alternative network-type detection makes the app identify both reported records as 5G SA and writes the current record to a separate `Cisco_Private_SIM2_*` log.
5. Treat the recovered map as a best-effort correction. For a publication-grade repeat, capture `dumpsys telephony.registry` alongside the drive or use modem diagnostic logging so serving-cell identity and SA registration are recorded unambiguously at each sample.
